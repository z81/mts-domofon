# Локальная проба распознавания и сбор диагностики

Отдельные CLI-утилиты для самостоятельных экспериментов. Офлайн-команды
`probe.py`, `compare.py`, `rank.py` и `benchmark.py` работают с локальными
данными, не запускают веб-камеру и не обращаются к API домофона.
Опциональный `watch.py` читает поток домофона и сохраняет кадры с лицами.
`dashboard.py` добавляет лёгкую страницу управления этим сборщиком.
Ни одна из этих команд не открывает дверь. Основной сервис и его Docker-образ
не меняются: для диагностики есть отдельный опциональный контейнер.

В офлайн-пробе без эталонов выполняется только детекция. С эталонами —
выравнивание по пяти точкам, нормализованные векторы и косинусное сходство
с каждым фото. По умолчанию используется buffalo_l. Эмбеддинги остаются
в памяти во всех режимах; изображения сохраняет только `watch.py`.
В отчётах остаются имена эталонов, координаты и scores.
Не публикуйте эти отчёты; каталоги `references/`, `models/`, `reports/` и `.venv/`
внутри этой папки исключены из Git. Для других расположений исключения не действуют.

## UI и Docker-сервис

UI показывает состояние процесса и потока, последние логи, скрин с метаданными,
события и историю запусков. Есть светлая/тёмная/системная тема. Это отдельный
Python HTTP-сервис и статическая страница, без Node, frontend-сборки, БД и CDN.
Модели загружаются только в дочерний процесс после нажатия **«Запустить сбор»**;
до этого камера не включается. После перезапуска контейнера сбор также выключен.

Нужен запущенный Docker/Colima и уже подготовленные модели в `models/`.
Положите эталонные фото в `scripts/face-probe/references/`: один альбом либо
подпапки по людям, как для CLI. Если эталонов пока нет, доступен режим
**«Только детекция лиц»**. Видео в папке эталонов не используется.

Из корня репозитория:

```shell
bash scripts/face-probe/service.sh up --build -d
```

Открыть **http://localhost:8765**. Выбрать режим, FPS, интервал скринов и
длительность, затем запустить сбор. Значение длительности `0` — до остановки
или лимита диска. Кнопка **«Остановить»** завершает сборщик и его ffmpeg, но не
общую HLS-сессию сервера. Повторный запуск не создаёт параллельный сборщик.

Для другой папки эталонов/адреса домофона:

```shell
FACE_PROBE_REFERENCES_DIR="/absolute/path/to/photos" FACE_PROBE_BASE_URL="http://host.docker.internal:3000" bash scripts/face-probe/service.sh up --build -d
```

Настройки подключения контейнера:

- `FACE_PROBE_REFERENCES_DIR`: каталог фото; по умолчанию `references/` рядом со скриптом.
- `FACE_PROBE_MODELS_DIR`: каталог подготовленных весов; по умолчанию `models/`.
- `FACE_PROBE_DATA_DIR`: отчёты; по умолчанию `reports/dashboard/`.
- `FACE_PROBE_BASE_URL`: origin основного сервиса, по умолчанию `http://host.docker.internal:3000`.
- `FACE_PROBE_PORT`: порт UI на хосте, по умолчанию `8765`.

Внутри контейнера адрес домофона должен разрешаться и быть доступным из Docker-сети.
Если приложение запущено на том же Mac, а LAN-имя недоступно из VM, можно явно
указать адрес хоста Docker с опубликованным портом приложения. Ошибки DNS/HTTP
видны в журнале; автоматического изменения сетевых настроек нет.

`service.sh` запускает контейнер с UID/GID текущего пользователя, чтобы читать
приватные файлы `0600` без изменения прав. При необходимости их можно явно
задать через `FACE_PROBE_UID`/`FACE_PROBE_GID`; они должны соответствовать владельцу
подключённых данных. Скрипт создаёт приватный каталог отчётов и стандартный пустой
каталог эталонов, если их ещё нет. Не запускайте helper через sudo.

Модели и фото подключены **read-only**, в образ не копируются. Контейнер работает
без root/capabilities, с read-only корневой ФС, лимитами 4 CPU и 2 ГБ RAM.
Эти лимиты — верхняя граница, а не постоянное потребление. Для инференса по
умолчанию используются 3 CPU-потока. PyTorch и инструменты экспорта в образ не входят.

UI по умолчанию доступен только с этого компьютера. Проверяются Host/Origin
и CSRF-токен, но это **не пользовательская авторизация**: не публикуйте порт
в интернет. Для удалённого доступа используйте защищённый туннель или отдельно
настроенный авторизующий reverse proxy. Дополнительное имя хоста UI допускается
только явно через `dashboard.py --allowed-host имя`; это не касается адреса камеры.

Каждый запуск: `reports/dashboard/session-…/`. В нём `service.json`, `worker.log`
и `capture/` с обычными отчётами сборщика. UI показывает последние 50 запусков,
200 событий и 150 строк процесса, обновляясь раз в 2 с; heartbeat сборщика — 5 с.
Один процесс обслуживает один каталог данных (защищено файловой блокировкой).
UI отображает только последний выбранный скрин, не загружает всю историю картинок.
Скрин остаётся в исходном разрешении/lossless: диагностическая точность пикселей
важнее дополнительного уменьшения. Статических растровых UI-ресурсов нет.

Лимит 1024 МБ относится к `capture/` одного запуска; дополнительно `worker.log`
ограничен 1 МБ. После этого новые строки процесса остаются только в ограниченном
буфере UI до перезапуска сервиса; структурированные события пишутся до лимита
сборщика. Предыдущие запуски не удаляются и в новый лимит не входят. Перезапуск
или удаление контейнера сохраняет отчёты в каталоге хоста.

```shell
bash scripts/face-probe/service.sh logs --tail 100
bash scripts/face-probe/service.sh stop
```

Без Docker, с уже подготовленным Python:

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/dashboard.py --references /path/to/reference.jpg
```

Адрес тот же, `http://localhost:8765`; данные по умолчанию в `reports/`.
Остановка сервиса — Ctrl+C, с завершением дочернего сборщика. Состояния ошибки,
лимита диска и прерванного запуска видны в истории, а не выдаются за успешный сбор.

## Сбор с домофона: FaceLiVTv2-L, без открытия двери

`watch.py` — отдельный процесс переднего плана, запускаемый вручную. Он не
устанавливает фоновый сервис и не меняет настройки основного приложения.
Нужны уже подготовленное Python-окружение, локальные веса FaceLiVTv2-L
и SCRFD, а также `ffmpeg` в PATH. При запуске ничего не скачивается.

Из корня репозитория, одной строкой (можно подставить уже подготовленный Python):

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/watch.py --references /path/to/reference.jpg
```

`--references` принимает одно фото или альбом с теми же правилами, что офлайн-проба.
Для каждого пригодного лица считаются cosine по всем меткам и эталонным фото.
Детекция — SCRFD; сопоставление — только **FaceLiVTv2-L**, CPU, FP32, 3 потока.
Для сбора только детекций замените `--references …` на `--detect-only`:
распознаватель и эталонные фото тогда вообще не загружаются.

Источник по умолчанию — `http://127.0.0.1:3000/api/v1/cameras/stream`.
Можно изменить только origin: `--base-url http://host:port`. Используются GET
стабильного адреса, его HLS-плейлиста и сегментов, без POST/DELETE. Поток выбирает
сам сервер: первая доступная камера выбранной квартиры. Скрипт использует
приложение только в доверенной локальной сети; не публикуйте этот API в интернет.
При обрыве/истечении HLS-сессии скрипт снова получает поток через стабильный адрес.
Тайм-аут открытия — 60 с, отсутствия кадров — 30 с; пауза повторов — от 2 до 30 с.

Основные настройки:

- `--fps 3`: анализ не чаще 3 кадров/с, не каждого исходного кадра. При перегрузке
  берётся последний полученный кадр; очередь не накапливается. Допустимо до 10 FPS.
- `--snapshot-interval 5`: сохранять кадр с хотя бы одним найденным лицом не чаще
  раза в 5 с, независимо от cosine. `0` сохраняет каждый проанализированный кадр
  с лицом. Пауза общая для всех лиц; это не трекинг отдельных людей.
- `--duration 300`: остановиться через 5 минут сбора; по умолчанию `0` — до Ctrl+C
  или лимита хранения. Загрузка модели и эталонов в это время не входит.
- `--max-mb 1024 --min-free-mb 256`: остановить сбор, если новый отчёт достигнет
  лимита или на диске останется мало места. MB десятичные. Старые отчёты не входят
  в этот лимит и не удаляются; ими нужно управлять отдельно.
- `--output /path/to/new-directory`: новый каталог, существующий не перезаписывается.
- `--det-size 640 --reference-det-size 640 --min-face 60 --min-eyes 20`:
  масштаб детекции и минимальные размеры пригодного лица/расстояния между глазами.

Результат — новый приватный каталог `reports/watch-…/` (права 0700, файлы 0600):

- `frames/*.webp` — исходные кадры с лицами без наложений и уменьшения,
  **lossless WebP**. Сохраняются именно анализируемые пиксели, чтобы дополнительное
  сжатие не искажало диагностику. Размер и разрешение каждого файла есть в метаданных.
- `frames/*.json` — данные соответствующего скрина: время, размеры, рамки,
  качество и scores каждого лица. Вырезки и эмбеддинги не сохраняются.
- `events.jsonl` — все проанализированные кадры с лицами, даже между скринами;
  события подключения/ошибок/повторов и heartbeat со счётчиками раз в 30 с.
  Кадры без лиц учитываются в счётчиках, но не пишутся по одному.
- `manifest.json` — настройки, контрольные суммы моделей, качество эталонов
  и описание значений. Адреса с идентификатором временной HLS-сессии не сохраняются.
- `summary.json` — причина остановки, длительность, число кадров, лиц и скринов.

Статусы лица: `scores_available` — вычислено сходство, `quality_rejected` —
фильтры качества не пройдены (причины в `rejectionReasons`), `detected_only` —
детекция без сопоставления. Даже отбракованные лица попадают в журнал и скрин.
`detectionScore` относится к наличию лица; `maxCosine`/`meanCosine` — сходство
с эталонами, **не вероятность и не процент точности**. `identityProbability`
всегда `null`: скрипт не выносит решения «это конкретный человек» и не задаёт
порог допуска. Нет трекинга и проверки живого присутствия.

Время `receivedAt`/`analyzedAt` — часы этого компьютера, UTC; время съёмки камерой
неизвестно (`cameraCapturedAt: null`). `receiveToAnalysisMs` — ожидание после
получения декодированного кадра, не задержка от камеры: буфер HLS в него не входит.
`detectionMs`, `comparisonMs`, `analysisMs` — локальное время обработки.
У лица также записываются размер, расстояние между глазами, резкость и яркость.

Остановка — **Ctrl+C**. Собственный ffmpeg останавливается, но общая серверная
HLS-сессия не удаляется: она может использоваться браузером и завершится по
серверному TTL. Коды выхода: 0 — Ctrl+C/заданная длительность, 1 — ошибка,
2 — лимит хранения. Нормальная остановка сама по себе не подтверждает доступность
камеры: смотрите `stream_connected`, `analyzedFrames` и ошибки подключения.

## Три модели одной командой

`compare.py` запускает **buffalo_l**, **antelopev2** и **AdaFace IR101 / WebFace12M**
последовательно, в отдельных процессах. У всех одинаковые детектор SCRFD, выборка
кадров, фильтры, CPUExecutionProvider и FP32. После каждого запуска процесс
завершается; пиковая память следующей модели не наследуется от предыдущей.

Один раз подготовьте окружение и веса (только этот этап требует сети):

```shell
python3 -m venv scripts/face-probe/.venv
scripts/face-probe/.venv/bin/python -m pip install -r scripts/face-probe/requirements-compare.txt
scripts/face-probe/.venv/bin/python scripts/face-probe/prepare_models.py
```

Можно использовать уже подготовленный Python вместо `.venv/bin/python`.
`prepare_models.py --reuse /path/to/existing/models` переиспользует имеющиеся
`det_10g.onnx` и `w600k_r50.onnx` после проверки SHA-256. Файлы копируются в
локальный игнорируемый каталог, а не связываются с временным каталогом. Повторная
подготовка проверяет готовые файлы, не скачивая их снова. Повреждённые или чужие
файлы автоматически не перезаписываются: их нужно явно переместить в сторону.

Запуск, одной строкой из корня репозитория:

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/compare.py /path/to/video.mp4 --references /path/to/reference.jpg
```

Вместо фото можно передать папку эталонов. По умолчанию масштаб детекции **640**
для видео и **640** для эталонов. Для видео с мелкими лицами можно отдельно
задать `--det-size 960`, сохранив `--reference-det-size 640` для крупных портретов.
Значения по умолчанию для видео в `compare.py` и старом `probe.py` различаются:
640 и 960 соответственно. При сопоставлении запусков явно задавайте один размер.

Выбор части моделей: `--model-set buffalo_l antelopev2`. Общий каталог весов
меняется через `--model-root`, остальные параметры выборки и фильтров совпадают
с `probe.py`. Фото, видео и сети в процессе сравнения не изменяются; скачиваний
при запуске `compare.py` нет. Не изменяйте входные файлы во время прогона.

Результаты сохраняются в новом `reports/compare-…/`:

- `comparison.md` и таблица в терминале: score и время лучшего кадра для каждой
  метки, медиана времени обработки кадра, общее время процесса и пиковая RAM.
- `comparison.json`: те же результаты, размеры весов, ссылки на отдельные отчёты,
  статусы ошибок и контроль совпадения выборки кадров/детекций между моделями.
- Подпапка каждой модели: `summary.json` и `frames.jsonl`; рядом — отдельный `.log`.

Таблица сохраняет заданный порядок моделей, **не ранжирует их по качеству**.
Если модель завершилась с ошибкой, остальные всё равно запускаются, в таблице
стоит `failed`, а общий код выхода ненулевой. Несовпадающая выборка тоже помечается
как незавершённое корректное сравнение. Ctrl+C останавливает текущий дочерний
процесс и сохраняет уже полученные результаты со статусом `interrupted`.

`Total` включает старт дочернего Python, импорты, загрузку весов, эталоны и видео;
скачивание и экспорт моделей в него не входят. `Frame median` включает детекцию,
фильтры и распознавание только прошедших фильтры лиц — это не чистое время
распознавания одного лица. Пиковая RAM включает загрузку модели, а не только
стабильное потребление во время инференса. Размеры весов в JSON относятся к
распознавателю; общий детектор занимает ещё около 17 MB.

## Рейтинг моделей по папке положительных и отрицательных роликов

`rank.py` прогоняет все установленные модели по видео в указанной папке.
По умолчанию имя `ya*` означает положительный пример, `clip*` — отрицательный,
без учёта регистра. Это заданная пользователем разметка, а не вывод скрипта.
Вложенные папки не обходятся; другие видео перечисляются как пропущенные.
Нужен хотя бы один ролик каждого класса. Префиксы можно изменить через
`--positive-prefix` и `--negative-prefix`.

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/rank.py ~/Downloads/s --references /path/to/reference.jpg
```

Вместо `.venv/bin/python` можно использовать уже подготовленное окружение.
`--references` обязателен: одно независимое фото или альбом **одной** метки.
Если есть подпапки нескольких людей, передайте нужную подпапку отдельно.
Фото-эталон должно быть независимым от оцениваемых видео.

По умолчанию анализируется **каждый декодированный кадр**, в том числе у видео
с переменной частотой или более 60 FPS. Это дольше прежнего режима 3 FPS.
Для быстрого прогона добавьте `--sample-fps 3`. Параметры `--start`, `--end`,
`--det-size`, `--reference-det-size`, `--min-face`, `--min-eyes`, `--threads`
общие для всех моделей и роликов. Масштаб детекции по умолчанию 640 для видео
и эталонов. Модели запускаются последовательно в отдельных процессах для каждой
пары «видео × модель»; память между запусками освобождается.

Устанавливать или скачивать веса команда не будет. Без `--model-set` выбираются
все имеющиеся распознаватели из `assets.py`; отсутствующие перечисляются отдельно.
Например, без локальных весов QCFace не попадёт в рейтинг. Повреждённые веса или
manifest приводят к ошибке предварительной проверки, а не к тихому пропуску.
Явный `--model-set buffalo_l antelopev2` ограничит прогон; отсутствие выбранной
модели — ошибка.

Проверка списка файлов, аргументов и контрольных сумм **без декодирования фото,
видео, инференса и создания отчётов**:

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/rank.py ~/Downloads/s --references /path/to/reference.jpg --dry-run
```

Результат — новый `reports/rank-…/`, путь печатается в начале и конце:

- `ranking.md`: рейтинг и матрица «каждый клип × каждая модель».
- `ranking.json`: те же метрики, средние значения для обоих классов, число
  упорядоченных/равных пар, оценки и время лучшего кадра, ошибки, ссылки на логи.
- `manifest.json`: список файлов, разметка, модели и общие настройки.
- `progress.json`: результаты уже завершённых задач, обновляется после каждой.
- `clip-001/`, `clip-002/`, …: полные покадровые отчёты и логи; соответствие
  порядковых номеров именам файлов записано в manifest.

За оценку ролика берётся **максимальный cosine** по всем подходящим лицам,
выбранным кадрам и эталонным фото. Каждый ролик имеет одинаковый вес в рейтинге.
Трекинга нет: если в кадре несколько людей, максимум может дать любое лицо.
Более длинное видео и больше эталонов дают больше шансов на случайный максимум.
Не меняйте видео, эталоны и веса во время прогона.

Место определяется по **ROC-AUC**: доле пар «положительный ролик / отрицательный
ролик», где положительный score выше, с половиной балла за равенство. Это позволяет
сравнить разделение классов без общей шкалы cosine между моделями. При одинаковом
ROC-AUC модели делят место. Значение 1.0 означает полное разделение **только этих
роликов**, а не 100% точность в реальном использовании. Например, 4 положительных
и 5 отрицательных роликов дают всего 20 пар, не 20 независимых людей.

`Positive min` — худший максимум среди положительных роликов; `Negative max` —
самый высокий среди отрицательных. `Gap = Positive min − Negative max`:
положительный зазор означает разделение классов на этих данных. Его величина
**не используется для сравнения качества разных моделей**. Ранжирование по
максимальному cosine тоже не используется. Скрипт не подбирает порог доступа.

Если в ролике нет подходящих лиц, score остаётся отсутствующим, **не нулём**.
Модель с пропущенными, ошибочными или необработанными роликами не получает
ROC-AUC и место; её доступные min/max — только диагностика оставшихся роликов.
При несовпадении выборки кадров/детекций между завершёнными запусками рейтинг
также не считается корректным. Ошибка одного запуска не останавливает остальные.
Ctrl+C останавливает текущий дочерний процесс и сохраняет частичный рейтинг.
Коды выхода: 0 — полный рейтинг, 1 — ошибка/неполное сравнение, 130 — прерывание.

Это маленькая экспериментальная выборка, не оценка вероятности ложного открытия.
Для независимой проверки результата нужны другие видео; подбирать модель и
объявлять её качество на тех же девяти роликах недостаточно.

## Чистая скорость распознавателей

`benchmark.py` по умолчанию измеряет CPU-задержку **на искусственном шуме 112×112**, без фото,
видео, камеры, детектора и сопоставления людей. Все установленные распознаватели
запускаются последовательно, каждый в отдельном процессе, с тем же загрузчиком
InsightFace/ONNX Runtime, CPUExecutionProvider, FP32, batch=1 и 3 потоками CPU.

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/benchmark.py
```

По умолчанию для каждой модели и каждого режима: 20 прогревочных вызовов и
200 измеряемых. Параметры: `--iterations 500 --warmup 30 --threads 3`;
`--model-set` ограничивает модели, `--model-root` меняет каталог весов,
`--output` задаёт новый каталог отчёта, `--seed` — генератор искусственного входа.
Новые зависимости и скачивания не нужны. Эталонные фото и сопоставление людей
не поддерживаются; отдельный режим одного видео описан ниже.

Два отдельных измерения используют одинаковый пул из восьми искусственных входов:

- `ONNX`: уже подготовленный FP32-тензор → сырой выход сети. Подготовка входа
  не входит в это время.
- `Aligned embedding`: уже выровненное BGR-изображение → подготовка входа,
  сеть, проверка вектора и L2-нормализация. **Выравнивание лица тоже исключено**.

Прогрев, импорты, загрузка модели и проверка SHA-256 не входят в задержку. Порядок
двух режимов чередуется, чтобы уменьшить влияние очерёдности. Во время замера
выполняются синхронные CPU-вызовы; GPU/CoreML не используются. Проверяется
совпадение результатов двух путей на искусственном входе, но векторы не сохраняются.

В `reports/speed-…/benchmark.md` — медиана, p95 (nearest rank), число обработок
в секунду и пиковая RAM; в `benchmark.json` и отдельных `summary.json` — также
все замеры, среднее, минимум/максимум, время загрузки, версии, хеши, настройки и
нагрузка системы. `progress.json` обновляется после модели, `.log` содержит ход
замера. Частичные результаты сохраняются при Ctrl+C; ошибка модели не мешает
остальным. Существующие отчёты не перезаписываются.

`Embeddings/s = 1000 / средняя задержка`: это последовательные обработки готовых
кропов, **не FPS камеры или всей системы**. Пиковая RAM включает импорты и загрузку
распознавателя, но без сессии детектора; она не равна RAM из видеопрогона.
Фоновые приложения и нагрев могут менять результат. Это локальный синтетический
замер производительности, а не проверка качества распознавания.

### Один клип: детектор и распознаватель раздельно

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/benchmark.py --video ~/Downloads/s/ya3.mp4 --model-set adaface_ir101 facelivtv2_l lvface_b
```

Один и тот же локальный файл декодируется **целиком, каждый кадр** для каждой
выбранной модели. Фотографии-эталоны не загружаются, сходство и идентичность
не вычисляются. Векторы сразу отбрасываются и не попадают в отчёт. Изображения
и вырезки тоже не сохраняются. Общий детектор SCRFD имеет размер входа 640,
фильтры — короткая сторона лица 60 px и расстояние между глазами 20 px,
как в стандартном видеопрогоне. Перед каждой моделью выполняются 20 искусственных
прогревочных вызовов детектора и распознавателя (`--warmup` можно изменить).

`--video` и `--iterations` взаимоисключающие: в видео число измерений определяется
количеством кадров и подходящих лиц. В `benchmark.md` отдельно показаны:

- ONNX median/p95: чистый вызов распознавателя **на одно подходящее лицо**.
- Face total median: выравнивание, подготовка входа, сеть и нормализация вектора
  **на одно лицо**.
- Detector median: детекция **на один кадр**, независимо от наличия лиц.
- Video seconds/FPS: фактическое полное прохождение ролика без загрузки моделей
  и прогрева. Это обработка файла офлайн, не скорость подключения к камере.

В JSON дополнительно есть время декодирования и обработки кадра, все отдельные
замеры, хеш видео, количество кадров/подходящих лиц и `processSeconds` с запуском
процесса, загрузкой весов и прогревом. Для проверки одинакового материала между
моделями сравниваются хеши видео и детекций. Если подходящих лиц нет, задержка
распознавателя остаётся отсутствующей, а не нулевой. Не меняйте файл во время прогона.

## Откуда берутся базовые модели

Ревизии, размеры и SHA-256 закреплены в `assets.py`. antelopev2 берётся из
[публикации Immich](https://huggingface.co/immich-app/antelopev2/tree/main/recognition),
а AdaFace — из [авторского CVLFace checkpoint](https://huggingface.co/minchul/cvlface_adaface_ir101_webface12m).

AdaFace загружается из `safetensors`, без pickle и `trust_remote_code`. Локальная
IR101-архитектура адаптирована из MIT-кода авторов; лицензия сохранена в
`LICENSE.cvlface.txt`. PyTorch используется только при подготовке ONNX-экспорта;
само сравнение всех трёх моделей выполняется через ONNX Runtime.
Экспорт проверяется на искусственном тензоре против PyTorch и сохраняет manifest
с хешами и версиями. Предупреждение PyTorch о legacy ONNX exporter само по себе
не является ошибкой; используется зафиксированная версия PyTorch.

Именно выбранный **CVLFace** checkpoint ожидает **RGB**, размер 112×112 и
нормализацию `(pixel / 255 - 0.5) / 0.5`. Это проверено по его конфигурации и коду
авторов. Не заменяйте его произвольным оригинальным BGR-checkpoint AdaFace.
Используется одна общая процедура 5-точечного выравнивания; TTA/усреднения
отражённых изображений в этой пробе нет.

На диске сохраняются и исходные safetensors, и ONNX: весь набор весов занимает
около 1 GB, без Python-зависимостей. MIT-лицензия на код не заменяет условия
использования весов: для InsightFace действуют ограничения модельной библиотеки,
для AdaFace нужно учитывать указанные авторами условия обучающего датасета.

## Дополнительные модели: LVFace, FaceLiVTv2, QCFace

Базовый набор по умолчанию в `compare.py` не изменён. В нём дополнительные модели
выбираются явно через `--model-set`; в один прогон можно включать базовые и новые
модели вместе. `rank.py` по умолчанию выбирает все установленные модели.
Установка использует то же окружение `requirements-compare.txt`, без новых
зависимостей и без изменений основного сервиса.

### LVFace-B и FaceLiVTv2-L

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/prepare_models.py --model-set lvface_b facelivtv2_l
scripts/face-probe/.venv/bin/python scripts/face-probe/compare.py /path/to/video.mp4 --references /path/to/reference.jpg --model-set lvface_b facelivtv2_l --sample-fps 60
```

`--sample-fps 60` обрабатывает все кадры обычного видео с постоянной частотой
до 60 FPS. Для видео с переменной частотой это целевая частота выборки.
Для безусловного режима «каждый кадр» используйте `--all-frames` вместо
`--sample-fps`; он поддерживается в `probe.py` и `compare.py`, а в `rank.py`
включён по умолчанию. В `summary.json` есть фактическое число кадров.

- `lvface_b`: авторский **LVFace-B / Glint360K**, готовый ONNX около 456 MB.
  Это не более крупная и не опубликованная здесь версия WebFace42M из статьи.
  [Источник весов](https://huggingface.co/bytedance-research/LVFace).
- `facelivtv2_l`: авторский **FaceLiVTv2-L / Glint360K**, исходный checkpoint
  около 36 MB. Конвертируется локально в ONNX; исходник тоже сохраняется.
  [Источник весов](https://huggingface.co/novendrastywn/FaceLiVT).

Обе модели получают RGB 112×112 с нормализацией `(pixel / 255 - 0.5) / 0.5`.
Детектор, 5-точечное выравнивание, фильтры и выборка кадров остаются общими.
FaceLiVTv2 загружается через `torch.load(weights_only=True)` со строгой проверкой
ключей и размеров. Локальная inference-архитектура адаптирована из кода авторов;
её лицензия сохранена в `LICENSE.facelivt.txt`. Загрузка удалённого Python-кода
при установке или анализе не выполняется. Экспорт сравнивается с PyTorch на трёх
искусственных входах, фиксируются хеши, ревизии и ошибка преобразования.
Специальная авторская reparameterization FaceLiVTv2 не включена; работают обычные
оптимизации ONNX Runtime. Это не воспроизведение опубликованных замеров скорости.

### QCFace IR100: нужен локальный checkpoint

На 23 сентября 2026 авторская ссылка на **QCFace-Arc-IR100** перенаправляет на
вход Microsoft. Автоматический скачиватель не обходит авторизацию, а случайные
веса не используются вместо обученной модели. Адаптер подготовлен, но без файла
авторских весов QCFace не считается установленной и не запускается.

Если доступ к файлу есть, скачайте его из раздела Pretrained Models
[официального репозитория](https://github.com/hpcc-hcmut/QCFace), затем:

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/prepare_models.py --model-set qcface_ir100 --qcface-checkpoint /path/to/QCFace-Arc-IR100.pth
scripts/face-probe/.venv/bin/python scripts/face-probe/compare.py /path/to/video.mp4 --references /path/to/reference.jpg --model-set lvface_b qcface_ir100 facelivtv2_l --sample-fps 60
```

Принимается доверенный PyTorch checkpoint IR100: словарь тензоров либо его поле
`state_dict`; поддерживаются префиксы `module.` и `backbone.`. Обучающая голова
`head.*` не экспортируется. Другие архитектуры и неполные веса отклоняются.
После успешной конвертации checkpoint копируется в игнорируемый `models/`, его
SHA-256 сохраняется в manifest. Это фиксация переданного файла, **не независимое
подтверждение его авторства**. Используйте только доверенные авторские веса.

QCFace использует опубликованные RGB mean `(0.5312, 0.4265, 0.3753)` и std
`(0.2873, 0.2555, 0.2496)`. Пересчёт из общего входа `[-1, 1]` встроен в экспорт,
поэтому дополнительная нормализация вручную не нужна. Inference-код адаптирован
из авторского IR100, см. `LICENSE.qcface.txt`. Здесь считается обычный cosine,
не отдельная quality-aware метрика QQCFace; flip-TTA не используется.
Проверка архитектуры на искусственных весах не проверяет качество распознавания
и не заменяет проверку реального checkpoint.

## Запуск

Один независимый эталон:

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/probe.py /path/to/video.mp4 \
  --references /path/to/reference.jpg
```

Несколько фото одного человека — плоская папка. Несколько людей — отдельные
подпапки; имя подпапки становится меткой в отчёте:

```text
scripts/face-probe/references/
  person_01/
    front.jpg
    glasses.jpg
  person_02/
    front.jpg
```

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/probe.py /path/to/video.mp4 \
  --references scripts/face-probe/references
```

Каждое фото должно содержать ровно одно обнаруженное лицо. Не смешивайте фото
в корне с подпапками людей. Поддерживаются JPEG, PNG и WebP; HEIC нужно заранее
экспортировать. Поворот из EXIF учитывается. Для честной оценки нужны независимые
эталоны, а не кадры оцениваемого ролика.

Только детекция, без вычисления сходства и загрузки распознавателя:

```shell
scripts/face-probe/.venv/bin/python scripts/face-probe/probe.py /path/to/video.mp4
```

Опции: `--start 12 --end 15` ограничивает временной диапазон;
`--sample-fps 3` задаёт частоту выборки, `--all-frames` включает каждый кадр
(взаимоисключающие опции); `--threads 3` — потоки ONNX на CPU;
`--reference-det-size 640` задаёт независимый масштаб детектора для эталонов;
`--output /path/to/new-report` — новый каталог результатов. Существующий каталог
не перезаписывается. Частота выборки не увеличивает FPS исходного видео.

## Что смотреть в отчёте

- `summary.json`: завершённый запуск, хеши/размеры моделей, настройки, число
  обработанных кадров, медианное время инференса, пиковая RAM процесса,
  лучший score и время кадра для каждой метки.
- `frames.jsonl`: одна JSON-запись на обработанный кадр, все обнаруженные лица,
  качество, причины отбраковки и сходство с каждым эталоном.
- Без `summary.json` запуск не завершён: частичный `frames.jsonl` не является
  готовым результатом. Ошибка даёт ненулевой код выхода.

По умолчанию для сравнения нужны короткая сторона лица не менее 60 исходных
пикселей, расстояние между глазами не менее 20 px и лицо без обрезки краем кадра.
Это экспериментальные фильтры, **не гарантия качества**. Размеры можно менять
через `--min-face` и `--min-eyes`. Sharpness и brightness — диагностические
показатели, без универсального порога. Для сравнения моделей сохраняйте одинаковые
настройки, эталоны и набор кадров.

`maxCosine` — максимальное сходство с одним эталоном данной метки;
`meanCosine` — среднее сходство по её эталонам. Score 0.8 не означает 80% точности.
Больше эталонов или кадров повышает шанс случайного максимума. Один лучший кадр
не подтверждает устойчивость, а доля кадров с найденным лицом — не точность
распознавания. Здесь нет автоматического решения «узнан», порога доступа,
трекинга одного человека между кадрами, защиты от фото/видео или управления замком.

Порог требует отдельных положительных и отрицательных примеров, включая очки,
освещение и другие ракурсы; одного положительного ролика недостаточно. Для будущей
интеграции потребуются отдельная оценка ложных допусков, защита от подделок,
подтверждение на последовательных кадрах одного трека и 30-секундная блокировка
повторного открытия.

`--recognizer /path/to/glintr100.onnx` позволяет подставить ArcFace-совместимый
распознаватель, например из antelopev2, сохранив тот же детектор. Подготовленный
`models/adaface_ir101/model.onnx` тоже совместим: его RGB-нормализация соответствует
используемому загрузчику. Это не относится к произвольным экспортам AdaFace.
Для LVFace-B, FaceLiVTv2-L и подготовленного QCFace IR100 используйте соответствующее
имя в `compare.py --model-set`; инструкции выше относятся только к указанным весам
и экспортам. Техническая проверка на искусственных данных не измеряет точность моделей.
Scores разных моделей нельзя напрямую трактовать как общую шкалу качества.
